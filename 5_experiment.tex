\section{Experiment}
\paragraph{Data construction.}
We construct \emph{query} and \emph{context} sets from the Yelp Open Dataset using a multi-stage curation pipeline designed to ensure data quality and relevance.

\textbf{Curation Pipeline.}
First, we interactively select a target city and specific cuisine categories (e.g., ``Italian'', ``Mexican'') based on restaurant density.
To ensure the selected entities genuinely fit the target categories, we employ an automated LLM-based filtering step.
Candidates are ranked by \emph{richness} (total volume of review text) and processed by an LLM which estimates the probability of category fit (0--100\%) based on keyword evidence extracted from their reviews.
We retain only restaurants with a high probability of fit.

\textbf{Review Sampling.}
For each selected restaurant, we construct a document set of up to 20 reviews.
To capture diverse user sentiments, we stratify the sampling by star rating, targeting 4 reviews from each star level (1--5 stars) where available.
Within each stratum, reviews are selected by descending text length to maximize the information available for reasoning.

\textbf{Metadata Structure.}
Each query corresponds to a single restaurant and includes:
(i) \emph{Item Metadata}: structured fields such as name, location, categories, attributes, and hours; and
(ii) \emph{Review Data}: the set of 20 sampled reviews, including text, rating, date, and reviewer profile signals (e.g., elite status, friend count, year started).

\paragraph{Contexts (User Requests).}
Each context corresponds to a natural-language user request that specifies a set of constraints, which must be supported by evidence available in the query. 
Rather than assuming a single notion of difficulty, we organize contexts into groups that isolate distinct combinations of evidence sources and logical structures. 
Requests vary by the types of information sources they reference: direct item metadata, computed metadata (e.g., hours or time-window constraints), review text, and reviewer or review metadata.

Requests consist of compositions of conditions connected by AND/OR operators (e.g., $A \,\mathrm{op}_1\, B \,\mathrm{op}_2\, C$).
Using this design, we construct 20 contexts grouped into 4 categories, each containing five requests, where each group isolates a specific combination of evidence sources (simple metadata, review text, computed metadata, social signals).

\begin{itemize}
    \item \textbf{G01 (R00--R04): Flat / Simple Metadata.}
    Requests use only direct item metadata (e.g., attributes, categories) with flat AND/OR composition.

    \item \textbf{G02 (R05--R09): Flat / Review Text.}
    Requests rely exclusively on conditions grounded in review text, composed using flat AND/OR logic.

    \item \textbf{G03 (R10--R14): Flat / Computed Metadata.}
    Requests use computed item metadata requiring interpretation (e.g., hours, time-window constraints) with flat AND/OR logic.

    \item \textbf{G04 (R15--R19): Flat / Social Metadata.}
    Requests use only reviewer or review metadata (e.g., elite status, recency) with flat AND/OR logic.
\end{itemize}

\paragraph{Baselines.}
We compare against 13 zero-shot prompting methods spanning two categories:
\emph{reasoning-based} methods that apply general problem-solving strategies (Chain-of-Thought, Self-Consistency, ReAct, Least-to-Most, Plan-and-Solve, Self-Ask, Decomposed Prompting),
and \emph{ranking-based} methods designed specifically for item selection (Pointwise, PaRaDe, Pairwise, RankGPT, Setwise, Listwise).
Details are provided in Appendix~\ref{app:baselines}.

\paragraph{Ground truth generation.}
For each (item, request) pair, we compute ground truth labels deterministically by evaluating leaf conditions against available evidence and aggregating via the request's Boolean structure.
For \texttt{review\_text} conditions, we use LLM-based judgments with symmetric consensus voting: a review is labeled positive ($+1$) or negative ($-1$) only if at least 75\% of non-neutral judgments agree.
Judgments are cached to ensure reproducibility.

\paragraph{Adversarial evaluation.}
To evaluate robustness, we apply attacks to review content $\mathbf{D}$ while preserving ground truth labels (computed from original, unattacked data).
Attack types include:
\begin{itemize}[nosep]
    \item \textbf{Typo corruption}: Random character transpositions (10--20\% rate)
    \item \textbf{Prompt injection}: Embedded commands (``IGNORE PREVIOUS INSTRUCTIONS...'')
    \item \textbf{Fake reviews}: Synthetic reviews with extreme, generic sentiment
    \item \textbf{Sarcastic manipulation}: Factually correct but misleadingly framed content
\end{itemize}
A robust method should maintain consistent performance across clean and attacked data.
